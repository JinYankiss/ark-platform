# 改写边界与已确认授权

> **授权已获得（2026-10-25）：用户对下面唯一的范围问题回复“可以”。允许文档行为实现和必要适配，但仍须区分来源，不允许无依据造上游 API。以下保留研究阶段的问题和验收清单；当前进展见 05/08 文档。**

## 1. 需要确认的唯一范围问题

用户同时要求：

1. 从零重写完整、可运行、带测试的企业平台；
2. 必须依据文档改写，不可以自己写代码；
3. Runtime 使用 Codex SDK。

已查到的来源没有构成一套能零适配拼接的同语言系统。**是否允许对“只有官方行为说明、没有公开源码”的部分按文档实现，并编写必要的项目适配代码，同时与上游源码移植和示例改写明确区分？**

这里不是请求放开为任意自研。核心机制仍必须先有来源；找不到依据的部分继续列缺口。也不能把恢复引擎等核心逻辑藏在“少量胶水代码”一词后面。资料不是最终代码交付，确认边界后才进入完整改写与测试。

## 2. 哪些能直接改写，哪些不能

| 模块 | 现有可改写依据 | 不能假装已经拿到的实现 | 必需的适配 |
| --- | --- | --- | --- |
| Codex Runner | O01–O04：官方调用/事件/恢复/信号实现 | 企业调度、远程控制、业务身份、Runner 容量 | 服务协议、任务与 thread 绑定、事件落库 |
| 飞书入口 | L01/L02：官方 dispatcher/adapter | Ark 消息幂等、内部用户/业务线映射 | 飞书事件到任务的转换、身份校验、异步回复 |

| 动态 Workflow | A01/D01：官方脚本示例；G03：公开定义/控制契约 | 四家完整的内部 replay/journal/sandbox Runtime | 需要选择真正可复用引擎，或获准按文档行为实现适配；不能复制类型声明就称引擎完成 |

| 目录/冻结 | M03：Go/PostgreSQL registry；M02：版本规则 | 能直接管理 Tool+Skill 的 TS 完整平台 | 能力元数据映射、制品解析、执行绑定 |
| 可观测/用量 | O01 usage、G07 Trace Context、D04 metrics、O05 OTel config | 已接通的飞书→Ark→Runner 跨服务链路 | 传播、导出、脱敏、去重、任务归因 |

## 3. 严格区分四种文件来源

后续每个关键模块的头部/旁置记录都应写明：

| 类型 | 允许声称什么 | 需要记录 |
| --- | --- | --- |
| 上游源码移植 | 从具体文件/函数改写 | 仓库、commit、path、原符号、许可证、改变了什么 |
| 官方示例改写 | 改写官方可执行示例 | 页面/示例、依赖 API、修改点、实际运行条件 |
| 文档行为实现 | 功能行为遵照说明，但不是官方引擎源码 | 明确行为段落、语义差异、测试；是否允许这类代码需本次确认 |
| 项目集成适配 | 本项目为了连接已有机制添加的逻辑 | 为什么必要、契约边界、不能归功给哪个上游；需本次确认 |

不允许：

- 自己编一个 in-memory Map 引擎，再在注释放 Dynamic Workflow 链接。
- 把 Copilot 的 `WorkflowContext` 类型当作已实现的持久化引擎。
- 把 Claude/Devin 的 `agent()` 原语当作已经安装可导入的开源依赖。
- 给 Codex SDK 添加不存在的 `registerTool`、`PreToolUse` 或 `defineWorkflow` API。
- 为了省事直接把 Runtime 换回 Claude Agent SDK 或 Copilot SDK。
- 把文件配置加载器包装成已建成远程配置中心。
- 在主服务进程里直接 eval 模型产生的脚本，并用 prompt 约束冒充隔离。

## 4. 名称可不同，语义不可以偷换

### Direct / 固定 Workflow / Draft

Direct 可以直接依 O03 改写。固定 Workflow 是复用已发布定义。Draft 是当前任务的临时定义，是否发布为固定版本是另一个动作。

这三种路径的组合路由并非在四家源码里找到的一段同名函数。来源 A02 只能支持路由模式，具体任务类型与策略属于本项目集成边界。

### 节点和依赖

A01/D01/G03 原生是程序控制流；有些依赖通过 await 形成，不是显式边数组。若需要简历所述通用 DAG 依赖解析，必须补充明确来源或承认表示层适配，不得称“这就是原版官方 Dynamic Workflow”。

### 取消 / 暂停 / 早停成功

- 停止浏览器/飞书展示不等于停止 Runner。
- 中止等待 SDK 返回不等于远程执行已终止。
- 暂停保留恢复资格，与取消不同。
- 正常提前成功需要结果验证，不能把 abort 异常翻译成成功。
- 本项目尚未决定跨服务取消与完成的仲裁策略；不能拿某一家局部 API 伪造通用结论。

### 三层恢复

1. **会话恢复**：恢复模型 thread（O01）。
2. **Workflow 恢复**：重放已完成步骤结果（D01/G03）。
3. **执行环境恢复**：工作目录、文件、凭据配置与运行环境（D02/D03）。

只恢复一个 thread_id 不代表三层都恢复。对外部建单/提交等副作用还需要幂等或回查，重放结果本身不提供 exactly-once 保证。

### 能力目录 / 工具集合 / 执行准入

目录是发现；ToolSet 是向 Runtime 暴露的集合；准入是实际调用边界。G09 特别说明单纯 registry ID 匹配的限制。只完成其中一层不能声称“能力池管理与安全准入全部完成”。

### 冻结版本

M02/M03 的已发布定义不可被同版本覆盖，是可直接对应的机制。`latest`、可移动分支、同 URL 的远程服务并不能自动保证执行内容冻结。

G03 `defineWorkflow` 深冻结的是内存元数据，不是自动把代码、工具与配置的外部依赖全部制品化。两者不能混为一谈。

## 5. 获准改写后必须补的测试

下列只是验收清单，**没有声称已编写或通过**。

### 端到端链路

- 真实 SDK 类型检查；离线 fake 与 live 入口明确隔离。
- 飞书无效凭据/加密事件、重复消息、不支持事件。
- 两个真实 Runner 进程竞争任务；领取失败不启动模型。
- Runner 进程宕机后认领过期与恢复。
- 入口到 Runner 的 trace 上下文传递；事件重复/断线重连。
- HTTP 取消控制到执行方 AbortSignal；取消后没有孤立模型执行。
- 完成与取消竞态；正常早停须有证据而非返回默认成功。

### Workflow

- Direct 不创建草稿；固定流程命中正确版本。
- 临时计划定义可检查；非法能力/输入在执行前拒绝。
- 串行、并行、pipeline 逐项推进；不误加全阶段屏障。
- 若采用 DAG，覆盖环/缺失依赖/非法重复节点；首先补来源。
- 已保存步骤恢复不调用模型；未保存步骤明确重跑。
- 重启恢复真正从存储加载，不用同一个对象假装重启。
- 暂停可恢复、取消不可恢复的既定语义；定义/配置变更不得混跑。
- 并发上限、总调用数、活跃超时、预算恢复计算。
- 外部副作用模糊成功时不直接重跑；失败与 null 语义一致。

### 能力与配置

- 唯一版本发布冲突；执行绑定不被 latest 更新改变。
- 按业务线限制目录和实际调用；同名来源工具不可越权。
- Tool 参数 schema、超时、错误、取消。
- Skill 元数据与正文实际注入；停用后不可调用。
- 恢复时重建所需 MCP/Skill 配置，无法重建明确失败。
- usage 事件幂等、版本归因、未知值不冒充零。
- 配置作用域、覆盖、运行快照、敏感值不入日志。
- 接入文档按真实命令和实际端口走通，而非只写漂亮目录树。

### 实测指标

- 1K+：真实任务流量或明确标注的负载测试，不能把测试用例数量当吞吐。
- 97%：先定义时间窗和分母；重试、取消、超时分别计数。
- 100+：真实可用且版本明确的能力清单，不生成占位能力凑数。

## 6. 实现顺序，不扩展简历范围

1. 先做真实 Codex/飞书适配和最小跨进程调度控制，让主链路能观察、取消和恢复。
2. 接固定流程、临时计划、执行依赖和检查点，逐项验证失败路径。
3. 贯通能力的注册→版本→准入→执行→用量，以及配置解析。
4. 只用少量知识库/建单/修复样例做闭环验收。

不开另一个产品，不引入无关组件，不把本次资料收集当最终交付完成。
